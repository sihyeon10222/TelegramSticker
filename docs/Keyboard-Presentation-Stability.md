# 키보드 표시·재진입 안정화 (2026-10-14)

## 2026-10-24 앱별 첫 전환 지연·앱 시작 로딩 후속

사용자는 1.0.4/5에서도 앱별 최초 키보드 전환에 약 2초의 깨진 이전 키보드 화면이 보이고, 이후 전환은 빠르다고 보고했다. 메인 앱의 실행마다 나타나는 목록 로딩과 간헐적 키보드 로딩은 이번 수정 전부터 있었다는 설명도 함께 기록한다. 실제 2초의 구간별 시간을 측정하지 않았으므로 모두 시스템 문제 또는 특정 함수 하나의 문제로 확정하지 않는다.

- 메인 앱의 `LibraryModel`은 메모리만 복원하고 새 프로세스에서는 비동기 전체 읽기까지 `isLoading` 상태였다. 이제 생성 시 로컬 index/manifest의 메타데이터를 읽어 설치 팩을 먼저 표시하고, 그 결과를 비동기 갱신에 재사용한다. 정상적인 설치 목록을 표시하기 위해 유지보수·네트워크를 기다리지 않는다.
- 앱·키보드가 쓰는 `LibraryReader.contents()`는 모든 스티커의 PNG·썸네일·원본 GIF·재생 GIF를 전수 stat하던 동작을 제거한다. 구조·상대 경로 검증은 유지하며, 비공개 파일 참조를 가진 `Sticker`가 실제 URL을 요청받을 때 기존 경로/symlink 검사를 수행한다. 배지·접근성·캐시 키·커버 생성은 파일을 열지 않는다. 쓰기·정리에서 사용하는 `snapshot()`의 기본 전체 검증은 유지한다.
- 키보드는 표시 전에 필요한 포스터만 기존 경로로 준비한다. 전체 라이브러리 파일 검사가 메인 스레드를 막던 비용을 줄이는 변경이며, OS의 확장 프로세스 시작이나 전환 스냅샷까지 없앤다는 의미는 아니다.
- `refreshPermission`에서 수행하던 접근 관찰 파일·defaults 동기 게시를 순차 백그라운드 큐로 옮긴다. 현재 UI의 전체 접근 판단은 즉시 유지하며, 관찰 기록 이후 Darwin 알림을 보내는 순서를 보장한다.

버전 1.0.5/빌드 6. 파일 형식·저장 경로·공유 컨테이너 권한·선택/최근 사용·revision 게시 정책은 유지한다. 테스트·수동 재현·성능 실측은 실행하지 않는다. 앱별 최초 2초 지연과 상단 시스템 여백의 실제 개선 여부는 미검증이다.

## 2026-10-24 첫 표시 포스터 준비 보완

첨부된 수정 가이드의 분석 시점과 현재 소스에는 차이가 있다. 현재 `KeyboardState.restoreLibrary()`는 이미 콜드 프로세스에서 검증된 라이브러리를 동기로 읽고, 컨트롤러는 표시 전 보이는 PNG를 준비한다. 아래 보완은 이 경로를 유지한다.

- 최초 읽기는 프로세스에서 한 번만 동기 시도한다. 실패해도 뒤따르는 `viewWillAppear`에서 메인 스레드 읽기를 반복하지 않고 기존 `reloadLibrary()`가 비동기로 재시도한다.
- 컨트롤러 생애 한 번만 사용하던 준비 완료 플래그를 매 표시의 준비 구간으로 바꾼다. 저장 스크롤 위치 적용 후 셀 레이아웃을 완료하고, `viewDidAppear`까지 현재 보이는 셀 중 이미지가 없는 셀에만 PNG를 준비한다(최대 64개, 팩 커버 최대 24개). 초기 호스트 배치가 바뀌면 새로 보이는 셀도 준비하며, 캐시가 비워진 뒤의 재진입도 같은 경로를 사용한다.
- 이미 표시 중인 이미지·GIF 프레임은 유지한다. GIF 타임라인과 화면 밖 이미지는 비동기 경로를 유지하고, 썸네일을 동기로 제공한 셀의 중복 이미지 작업은 취소한다. `StickerImages.preparePosters`는 이미지가 없는 셀의 포스터 준비에 계속 사용한다.
- 기존 `PointsOfInterest` 카테고리의 `Keyboard First Poster`는 첫 `loadView` 또는 이후 `viewWillAppear`부터 보이는 셀의 이미지 할당까지 측정한다. `cachedLibrary`로 라이브러리 메모리 재사용 여부를 구분하고, 종료의 `outcome`으로 이미지 할당·빈 선택·읽기 실패·표시 취소를 구분한다. OS의 실제 화면 합성 완료나 프로세스 실행 이전 시간은 포함하지 않는다. `Initial Library Restore`와 `Presentation Posters`는 동기 읽기/상태 복원과 포스터 준비 비용을 분리한다.

빌드 제공 버전은 1.0.4/빌드 5다. 자동·수동 테스트와 Instruments 실측은 실행하지 않는다. 큰 라이브러리의 시작 시간이나 실제 깜빡임 소멸은 미검증이며, 추가 스냅샷 저장·파일 검증 지연·GIF manifest 확장은 도입하지 않았다. 시스템 소유 상단 여백은 아래 기록과 같이 미해결로 남는다.

## 2026-10-22 상단 여백 두 상태 재확인 — 미해결

첫 진입의 로딩 페이지 교체 경로를 수정한 이후에도 사용자는 시스템 한글·영어·스티커 키보드 왕복 시 팩 줄 위의 여백이 두 상태로 표시된다고 보고했다. 이번에는 사용자 지침에 따라 테스트·수동 재현을 실행하지 않고 현재 소스·기존 측정 기록·공개 SDK를 대조했다.

- 현재 `StickerKeyboard/KeyboardViewController.swift`는 콘텐츠 상단을 루트 `view.topAnchor + 4pt`에 고정한다. 내부 상단 여백을 진입·선택에 따라 0/17pt로 바꾸는 분기는 없다. `needsInputModeSwitchKey`에 따른 32/44pt 팩 줄 높이 차이는 전환 버튼의 최소 터치 영역이며 루트 바깥의 여백과 구분한다.
- 위의 사용자 설명은 아래 10월 14일 기기 기록의 확장 루트 바깥 17pt 변화와 일치한다. 현재 빌드에서 외부 여백을 새로 측정해 원인을 확정한 것은 아니다.
- 설치된 iOS 27.1 SDK의 공개 `UIInputViewController.h`·`UIInputView.h`와 [Apple 키보드 레이아웃 문서](https://developer.apple.com/documentation/uikit/configuring-a-custom-keyboard-interface)를 확인했다. 확장 primary view의 높이 조절은 제공하지만 호스트의 상단 inset을 고정·초기화하는 API는 확인하지 못했다.
- [동일 현상의 개발자 측정 보고](https://developer.apple.com/forums/thread/843093)는 이전 시스템 키보드에 따른 17pt 차이, 확장 bounds·safe area 불변, 높이·스타일·self sizing 변경으로 해결되지 않는 사례를 설명한다. Apple의 수정 보장이나 공식 우회책으로 해석하지 않는다.
- 이미 실패한 높이 재요청·fitting override·임의 음수 여백 보정을 반복하지 않는다. 확장 내부 배치가 일정한 사실을 시스템 배경 상단까지 일정해졌다는 증거로 삼지 않는다.

앱 코드·프로젝트 설정·저장 데이터는 변경하지 않았다. 새 빌드·설치·테스트는 실행하지 않았으며 이 항목은 미해결이다. 이전 첫 진입 로딩 수정의 빌드·설치 결과와 이번 외부 여백 문제의 해결 여부를 구분한다.

## 2026-10-17 기본 높이 전환 회귀 복구

사용자 사진에서 기본 높이 전환 이후 팩 줄만 표시되고 스티커 viewport가 접힌 것을 확인했다. UICollectionView의 콘텐츠는 intrinsic height를 제공하지 않으므로 상하단을 연결하는 것만으로 충분한 키보드 높이가 보장되지 않는다. 기본 높이에 맡기는 직전 변경을 철회하고 원래의 UIInputView(.keyboard)·allowsSelfSizing 및 루트 높이 제약(세로 240pt·가로 200pt·접근성 380pt, 우선순위 999)을 복구한다.

첫 시도에 추가했던 fitting override와 viewDidAppear 제약 재게시는 제외한다. 라이브러리 복원/썸네일 준비의 중복 제거와 권한 관찰 guard 수정은 유지한다. 파일·저장 경로·타깃 변경은 없다. 아래 기본 높이 전환 설명은 현재 구현이 아닌 실패한 시도의 이력이다. 새로 만든 접힘 회귀를 되돌리는 변경이며 기존 세 현상의 해결을 의미하지 않는다. 사용자 지침에 따라 테스트는 실행하지 않는다.

## 2026-10-17 재수정 — 기본 시스템 높이로 복귀

사용자는 직전 설치에서도 세 현상이 모두 그대로라고 확인했다. 직전 fitting override와 viewDidAppear 높이 재게시로 해결됐다는 근거는 없으며 해당 구현을 제거했다. 새 캡처는 시스템 글쇠의 상단 잘림뿐 아니라 스티커 표시 후 키보드 배경 상단과 콘텐츠 배치가 다시 달라지는 구간을 보여 준다. 시스템 문제만으로 전체 현상을 설명한 이전 판단은 충분하지 않다.

- UIInputViewController가 생성하는 기본 루트와 시스템 기본 높이를 사용한다. loadView, allowsSelfSizing, fitting override, 240/200/380pt 높이 제약 및 부착 이후 높이 재요청을 모두 제거한다. 확장에서 키보드 교체 중 호스트 높이를 추가로 변경하는 경로를 없앤다.
- 그리드는 현재 bounds에 맞추고 최대 네 행·최소 44pt 셀 정책을 유지한다. 시스템이 작은 영역을 주면 표시 행 수가 줄 수 있다. 접근성 셀/팩 줄 크기는 유지한다.
- 라이브러리 복원은 viewWillAppear에서만 실행한다. viewDidLoad에서 먼저 복원한 뒤 같은 진입에서 index를 다시 읽던 경로와 중복 첫 페이지 썸네일 준비를 제거한다. 선택/순서/revision 복원과 파일·symlink 검증은 유지한다.
- 접근 권한 확인 자체는 레이아웃 시 계속하되 공유 기록 읽기/게시와 defaults synchronize는 표시 시작 또는 권한 변경 시에만 실행한다. 이전 구현은 상태 변경 guard 전에 공유 기록을 읽고 있었다.

자동·수동 테스트는 사용자 지침에 따라 실행하지 않는다. 빌드·설치 성공은 깜빡임·빈 키보드·상단 여백의 해결 판정이 아니다. 아래 기록은 이전 구현과 당시 결과다.

## 2026-10-17 후속 — 초기 높이 측정 명시

아래 10월 14일의 “기본 UIInputView fitting 유지” 설명은 이번 변경으로 대체한다. 새 사용자 자료는 직접 열 때 확장 내용이 사라지고 시스템 지구본/마이크만 남는 경우, 상단 여백 차이, 시스템 키보드 전환 중 재배치를 보여 준다. 자료만으로 첫 현상의 원인이 높이 협상인지 확장 종료인지 확정할 수는 없다.

- 같은 컨트롤러 파일 안의 StickerKeyboardInputView에서 두 fitting 메서드가 요청 높이를 명시한다. 높이 제약과 같은 세로/가로/접근성 값을 사용하고, 실제 호스트 bounds를 요청값으로 되먹이지 않는다. intrinsic size 재정의는 없다.
- 루트의 flexibleHeight autoresizing을 제거한다. 필수 호스트 제약보다 낮은 999 높이 제약은 유지한다.
- 부착 후 viewDidAppear에서 팩 줄과 최소 44pt 그리드 행도 들어가지 않는 높이일 때 기존 높이 제약을 한 번 재게시한다. 정상적으로 좁은 호스트 크기에는 반복 복구 루프를 걸지 않는다.
- 첨부 영상의 정확한 시간 프레임을 확인하면 스티커 표시 전에 한글 키보드의 Siri 줄이 사라지고 글쇠가 위로 이동한다. 이 이전 키보드 구간은 확장의 자체 레이아웃만으로 해결됐다고 판단하지 않는다.
- 상단 약 17pt 차이는 [동일 현상의 개발자 측정 보고](https://developer.apple.com/forums/thread/843093)와 일치하지만, 이번 사용자 기기의 호스트 계층을 직접 측정한 결과는 아니다. 임의 음수 여백이나 호스트 내부 뷰 변경은 하지 않는다.

이번 작업에서는 요청에 따라 자동·수동 테스트를 실행하지 않는다. 수정은 빌드와 기존 데이터 유지 설치 대상으로 제공하며 실제 간헐적 현상의 소멸은 미검증이다. 아래 테스트 결과는 10월 14일 당시의 기록이다.

## 이전 상태 — 2026-10-14 영상 비교 및 실기기 검사 후

**내부 배치·선택 유지 검사는 통과했지만, 시스템 전환 시의 상단 17pt 여백과 모든 깜빡임이 해결된 상태는 아니다.** 아래 이력의 fitting size 및 16ms 썸네일 준비 방식은 현재 구현에서 대체했다.

### 최종 코드

- 기본 `UIInputView(.keyboard)`와 루트 높이 제약 하나(우선순위 999)를 사용한다. 별도 `KeyboardInputView`의 intrinsic/fitting size 재정의는 제거했다. 일반 세로 240pt, 가로 200pt, 접근성 380pt 선호값을 유지하며 시스템의 필수 크기 제약을 덮지 않는다.
- 루트 내부 상단·좌우는 4pt, 하단은 0pt다. 별도 콘텐츠 높이 제약이나 호스트 크기를 다시 요청 높이로 보내는 피드백은 없다. 실제 그리드 bounds를 기준으로 7열·4행을 계산한다.
- 첫 페이지의 작은 PNG 썸네일 최대 28개를 표시 전에 준비한다. 16ms가 지나면 중간에 끊던 경로를 제거해 마지막 몇 셀이 빈 상태로 먼저 표시되는 원인을 줄였다. GIF 전체 프레임을 동기적으로 읽지는 않는다.
- 선택·최근 사용·팩 순서·revision을 표시 전에 복원하며, 같은 목록은 다시 만들지 않는다. 늦은 이미지/페이지 콜백의 세대 검사, 인터럽트 가능한 스와이프, 스크롤 중 GIF 재생은 유지한다.

- Swift Testing 60개: 실패 0(명시적 실행이 필요한 실제 서버 검사 2개 제외). 별도 XCTest 라이브러리 성능 검사 1개 통과.
- Simulator: 직접 열기·시스템 키보드 왕복 2회·앱 재실행의 내부 배치/선택 검사 통과. 대각선 스크롤과 가로 팩 전환 회귀 검사 2개 통과.
- iPhone 15 Pro / iOS 27.2: Release 코드로 시스템 키보드 왕복 4회와 앱 재실행 검사 통과. 모든 측정에서 루트 `(0,537,393,240)`, 팩 줄 `(4,541,347,32)`, 그리드 `(4,575,385,202)`로 동일했다. 설치된 GIF 팩과 선택을 유지했다. 개인 채팅이나 클립보드를 읽지 않았다.
- 서명 검사와 실기기 앱 업데이트 성공. 팩/설정 삭제 없이 기존 앱에 덮어쓴다.
- 개발 중 Simulator의 하드웨어 키보드 모드 때문에 소프트웨어 키보드가 숨겨진 검사 실패가 있었다. 모드를 해제한 뒤 재검사했다. 해당 실패를 앱의 높이 회귀로 판단하지 않는다.

### 남아 있는 시스템 영역의 차이

좌표 검사 통과는 전체 화면 모양이 같다는 의미가 아니다. 사용자 영상과 이번 Simulator/실기기 스크린샷 모두에서 다음을 확인했다.

1. 직접 열기와 시스템 키보드에서 전환한 뒤의 **확장 루트와 스티커 위치는 같다**.
2. 시스템 키보드에서 전환하면 확장 루트 위로 배경만 약 51px(@3x), 즉 17pt 더 올라간다. 직접 재실행해 열면 그 추가 영역이 사라진다.
3. 최소 높이 제약과 `allowsSelfSizing=false`도 Simulator에서 같은 차이를 남겼다. 효과가 없는 보정은 최종 코드에 넣지 않았다.
4. 따라서 화면 밖으로 콘텐츠를 이동하거나 임의로 17pt를 빼는 방식은 적용하지 않는다. 여백이 없는 경우의 정상 배치와 터치 범위를 깨뜨릴 수 있다.

[Apple Developer Forums의 동일 현상 보고](https://developer.apple.com/forums/thread/843093)는 iOS 27에서 이전 시스템 키보드에 따라 **호스트가 소유한 top inset만 17pt 달라지고 확장 bounds는 그대로**인 측정 결과를 제시한다(FB24460699, FB21449121 등). 이는 다른 개발자의 직접 측정 보고이며 Apple의 공식 해결 확인이나 보장으로 취급하지 않는다. 현재 확인한 공개 API 범위에서 이 호스트 inset을 확장이 초기화하는 방법은 찾지 못했다.

수정 후 카카오톡·메모 각각의 전체 전환 영상과 시스템 첫 프레임까지의 깜빡임 소멸은 최종 검증하지 못했다. 이 항목은 미해결로 유지한다.

### 재검사 명령

Simulator는 `KeyboardUITests/testDirectOpenAndSystemKeyboardReturnUseSameContentGeometry`를 실행한다. 실기기는 `PhysicalKeyboardPerformanceTests/testInstalledKeyboardPresentationAcrossSystemSwitches`를 명시적으로 선택하고 테스트 runner 환경의 `STICKERBRIDGE_KEYBOARD_PRESENTATION=1`로 활성화한다. 실기기 검사는 fixture를 설치하거나 팩/최근 사용을 변경하지 않는다. 결과의 screenshot attachment와 실제 배경 경계도 함께 확인해야 하며, 내부 좌표의 동일성만으로 상단 여백이 사라졌다고 판정하지 않는다.

## 이전 변경 이력

사용자 요청에 따라 간헐적 현상의 반복 재현 대신, 확장 전체의 상태·레이아웃·비동기 작업 수명을 검토했다. 아래는 코드에서 확인한 위험 경로와 변경 사항이며 모든 앱에서 같은 현상의 원인이 확정됐다는 뜻은 아니다.

## 정리한 경로

1. **남아 있는 컨트롤러의 오래된 상태**: 선택은 `viewDidLoad`에서만 읽고 최근 사용·팩 순서는 저장소 객체 생성 때만 읽었다. 다른 세션 이후 재사용될 때 최신 상태와 달라질 수 있었다. 매 표시 전에 선택·최근 사용·순서·공유 revision을 동기적으로 확인한다. 최근 사용 기록도 최신 목록에 합친다.
2. **첫 화면 이후의 목록 교체**: 재진입 시 비동기 조회를 시작하던 경로를 제거했다. 새 revision은 표시 전에 준비하고 같은 revision/선택/항목이면 탭·셀을 재생성하지 않는다. 일시적인 읽기 실패는 기존 목록이나 저장된 선택을 삭제하는 근거로 사용하지 않는다.
3. **초기 높이 협상과 불필요한 reload**: `KeyboardInputView`의 fitting size·intrinsic size와 초기 높이 제약이 같은 선호값을 사용한다. 제약은 뷰 생성 시 설치하고 호스트의 필수 제약보다 낮은 우선순위를 사용한다. 일반 세로 240pt·가로 200pt·접근성 380pt 선호값은 유지한다. 변경 없는 레이아웃에서는 reload하지 않으며 바뀐 그리드 크기는 그리기 전에 재계산한다. UIKit은 기기/창 제약에 따라 실제 높이를 결정할 수 있다.
4. **비운 셀·재시작한 GIF**: 셀의 첫 프레임에 캐시된 썸네일을 바로 제공한다. 컨트롤러 간 공유 캐시는 8MiB 비용 한도를 사용한다. 첫 화면의 대표 이미지와 최대 28개 썸네일만 16ms 준비 예산 내에서 읽으며 나머지는 비동기 처리한다. 화면 밖 셀의 재생은 멈추되 마지막 이미지는 재사용 전까지 유지한다. 같은 GIF의 반복 configure는 현재 프레임·타임라인을 초기화하지 않는다.
5. **늦게 도착한 결과**: 이미지 콜백은 스티커 ID뿐 아니라 셀 구성 세대를 검사한다. 동일 ID의 새 revision에도 옛 이미지가 적용되지 않는다. 팩 전환 완료/정리 콜백과 라이브러리 작업도 표시 상태·세대를 검사한다. 닫힘·재진입·새 선택 후 이전 작업이 화면을 되돌리지 않는다.
6. **남은 터치 상태**: 닫을 때 관성 이동과 진행 중 전환을 정리한다. 재진입 시 이전 하이라이트·복사 배지·임시 안내를 유지하지 않는다.
7. **빈 라이브러리**: 파일이 아직 없는 정상 빈 상태에 임의의 새 UUID를 매번 만들지 않는다. 빈 목록이 매 재진입마다 새 revision으로 취급되는 것을 막는다.

시스템 지구본·마이크와 키보드 전환 API, 투명한 스티커 배경, 스크롤 중 GIF 재생은 유지한다. 개인정보·채팅 문맥·기존 클립보드를 읽지 않으며 스크린샷 캐시나 비공개 UIKit API로 시스템 전환을 조작하지 않는다.

## 공식 API 근거

[`allowsSelfSizing`](https://developer.apple.com/documentation/uikit/uiinputview/allowsselfsizing)는 `systemLayoutSizeFitting(_:)`의 크기를 UIKit에 제공하는 공식 경로다. [`UIInputView`](https://developer.apple.com/documentation/uikit/uiinputview)의 keyboard style을 유지하며 사설 높이·스냅샷 API는 사용하지 않는다.


## 추가 수정: 다섯 가지 사용자 피드백

- **선택한 팩 복원**: 마지막 선택을 확장 자신의 Application Support에 512바이트 이하 JSON으로 원자적으로 저장한다. 다른 호스트 프로세스의 UserDefaults 전파 지연에 의존하지 않는다. 기존 preference는 호환용 fallback으로 유지한다. 상단 탭 줄의 실제 너비와 버튼 위치가 정해진 후 선택한 탭을 화면 안으로 이동한다.
- **최초 레이아웃**: 호스트가 초기 연결 중 임시로 큰 높이를 줄 때 내용까지 전체 화면 높이로 늘어나지 않도록 콘텐츠 높이를 제한한다. 그리드 layout은 bounds 크기가 바뀌는 시점에 무효화한다. 루트 뷰에서 클리핑한다.
- **빠른 연속 스와이프**: 제스처는 이동하는 셀이 아닌 고정 viewport에서 받는다. 상호작용·중단 가능한 UIViewPropertyAnimator를 사용한다. 손을 놓을 때 선택 의도를 바로 저장하고 다음 스와이프가 들어오면 이전 확정 페이지를 적용한 뒤 이어서 처리한다. 이전 60ms 지연 정리를 제거했다.
- **앱 첫 목록**: LibraryModel 생성 시 게시된 index/manifest 메타데이터를 읽어 설치된 목록을 준비한다. recover·재생용 파일 생성 완료를 기다리지 않는다. 이 경로는 이미지 파일 전체를 stat하지 않으며, 실제 이미지를 열 때에는 기존 symlink·경로 검사를 거친다.
- **하단 활용**: 확장의 primary view 끝까지 그리드를 배치하고 추가 bottom inset 4pt를 제거한다. 네 행 높이를 남은 공간에 맞춰 배분한다. 시스템 지구본·마이크 영역 밖으로 확장을 그리지 않는다.

추가 단위 검사: 서로 다른 preference를 가진 두 호스트의 즉시 선택 복원, 앱 비동기 정리 실행 전 설치 목록 존재, 빠른 메타데이터 경로의 경로 순회 차단. 전체 검사 58개 실행(실제 서버 opt-in 2개 제외), 실패 0. 7×4·하단 채움·좌우 전환 UI 검사 2개 통과. iPhone 15 Pro용 Release 빌드·서명 검사·설치·앱 실행 성공. 설치 후 이전 StickerKeyboard 프로세스가 남아 있지 않음을 확인했다. 앱별 간헐적 현상을 재현하여 소멸을 판정한 결과는 아니다.


## 사진 비교 후 여백 조정

- 일반 팩 줄 높이 36→32pt, 버튼 폭 44→36pt, 세트 간격 4→2pt. 접근성 크기와 자체 지구본이 필요한 기기의 높이는 유지한다.
- 상단·좌우 바깥 여백을 4pt로 통일하고 관리 버튼 폭을 44→36pt로 줄인다.
- 정상적인 호스트 뷰 높이는 모두 활용한다. 초기 연결 중의 비정상적으로 큰 임시 높이만 제한한다. 실제 뷰가 선호 높이보다 조금 큰 경우 콘텐츠 위쪽에 고정 높이 차이만큼 여백을 남기지 않는다.
- 스티커 이미지 안쪽 여백 3→1pt. 7열·4행과 하단 inset 0을 유지한다. 시스템 지구본·마이크가 있는 primary view 바깥 영역은 덮지 않는다.

- 콘텐츠 높이 제약은 루트 키보드 높이 제약보다 낮은 우선순위로 설정한다. 호스트의 임시 크기가 콘텐츠를 통해 다시 키보드 높이로 전달되는 경로를 차단했다.
- 최종 Simulator 검사 통과. 측정된 primary view `(0,641,440,240)`, 팩 줄 `(4,645,394,32)`, 그리드 `(4,679,432,202)`: 상단·좌우 4pt, 하단은 primary view 끝까지 채운다. 최종 스크린샷을 확인했고 Release 빌드·iPhone 설치·실행 성공.


## 호스트 앱별 행 수·잘림 차이 수정

사용자 사진에서 카카오톡은 다음 행이 걸리고 메모는 마지막 행이 잘리는 차이가 확인되었다. 앞선 단일 Simulator 화면의 검사만으로 앱별 표시가 같다고 판정할 수 없었다.

현재 구현은 이전의 콘텐츠 높이 제한·실제 높이 피드백과 FlowLayout delegate 크기 계산을 대체한다.

- `Shared/StickerGridLayout.swift`의 UICollectionViewLayout이 실제 collection view bounds로 열·행·셀 높이를 매 prepare마다 계산한다. FlowLayout delegate metric cache를 사용하지 않는다.
- 동일한 UIKit collection view에서 높이 218→202→194→182→218→202pt를 연속 적용하여 각 단계의 첫 28개가 정확히 네 행으로 맞는지 검사한다. 너비 320pt·높이 140pt 같은 짧은 영역은 최소 터치 크기를 유지하는 세 행으로 계산한다.
- 화면 밖 전체 스티커의 attributes를 만들지 않고 교차하는 행의 attributes만 생성한다. 팩 경계의 새 줄·6pt 간격과 스크롤·재사용은 유지한다.
- 콘텐츠를 primary view의 상단 4pt·하단 0pt에 직접 고정한다. 콘텐츠 높이를 다시 키보드의 요청 높이로 보내는 별도 제약·계산은 제거했다. 루트 선호 높이는 기존 240/200/380pt를 유지하며 호스트가 실제로 배정한 영역 안에서 계산한다.
- 재진입 시 선택 팩을 유지하되 스크롤은 첫 행에서 시작한다. 다른 뷰포트 높이에서 남은 중간 행 offset을 사용하지 않는다.
- 단위 검사의 짧은 뷰포트 예상 열 수는 처음 6열로 잘못 작성되어 실패했다. 320pt에는 44pt 7열과 2pt 간격이 정확히 들어가므로 기대값을 7열로 수정했다. 높이 변경 네 행 검사 자체는 처음부터 통과했다.

카카오톡·메모의 실제 기기 결과를 이번 단위 검사 결과로 대체하지 않는다. 최종 실행 결과는 아래에 추가한다.

- 최종 결과: 전체 단위 검사 60개 실행(선택적 실제 서버 검사 2개 제외), 실패 0. 높이 변경·짧은 뷰포트 검사 2개를 최종 폭 계산 후 다시 실행해 통과했다. 대각선 스크롤·좌우 전환·7×4/팩 구분·GIF 표시 UI 검사 4개 통과. Release 빌드·서명·iPhone 설치 성공. 카카오톡·메모 실기기의 최종 표시 결과는 미검증으로 남긴다.
